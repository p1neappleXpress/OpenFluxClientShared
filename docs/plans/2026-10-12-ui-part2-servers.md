# Новый интерфейс, часть 2: свой сервер, мастер и редактор ноды — план

**Spec:** `docs/specs/2026-10-12-ui-redesign-design.md`, разделы 5.1–5.5 (с поправкой 5.2 ниже), 3, 4.2.
**Основа:** часть 1 (`app/theme`, `app/components`, `app/nav`, `app/shell`).
**Исполнитель:** этот же сеанс, inline. План — решения, задачи и тесты; код пишется по TDD прямо в задачах (Ruling: подробные листинги кода в плане не нужны, исполнитель тот же, что автор, — цена: ниже переносимость плана на другого исполнителя).

## Поправка к спецификации 5.2 (Ruling)

RPC ядра для мастера (`OpenFlux/node_wizard.go`) не умеет `upgrade`, `autoupdate`, `uninstall`; ядро не меняется (spec 2). Поэтому вкладка «Сервер»: строка «система · версия ядра · автообновление вкл/выкл» (из `ServerProbe`), «Изменить доступ», «Забыть сервер». Автообновление ядра меняется при установке ноды (`apply(autoUpdate)`), переключатель — в форме новой ноды. Обновление ядра и полное удаление OpenFlux с сервера — вне этой работы (новая задача N6).

## Найденная ошибка старой архитектуры (исправляется)

`AppContainer.nodeWizard` — **одно** SSH-подключение на приложение, а старый `NodesScreenModel` держал по `NodeWizardModel` на сервер: при двух открытых серверах вызовы одного шли через подключение другого (переподключение — только после 60 с простоя). Новая модель: одно `ServerLink` на приложение, которое помнит, к какому серверу открыто, и перед каждым вызовом переподключается, если просят другой сервер.

## Устройство

```
app/servers/
  ServerLink.kt        одно SSH-подключение: connect(target)/ensure(serverId)/call{}/close; повтор после простоя,
                       переподключение к другому серверу, sudo, отпечаток ключа; список нод (probe + showChannel)
  NodeDraft.kt         что человек выбрал для ноды: имя, транспорты (вкл + ссылка), режим, автообновление;
                       toTransports(): Result<List<NodeTransport>>; changes(original): Int — чистая логика
  NodeVerifier.kt      проверка ноды как клиента: подключиться, выход с адреса сервера, ждать основной транспорт
  ServerViewModel.kt   экран сервера: состояние подключения, ноды, действия (подключить себе, поделиться, удалить)
  NodeEditorModel.kt   редактор ноды (создание и изменение): черновик, «Применить»/«Установить», ход, ошибка
  AddServerModel.kt    форма входа и «Быстро / Настроить»
  Adopt.kt             профиль ноды на устройстве: найти по ключу/адресу или собрать из ключа сервера
  screens: ServersScreen, AddServerScreen, ServerScreen, NodeScreen (+ NewNode), HostingScreens, ThisDeviceScreen
app/nav/Dest.kt        + AddServer, NewNode(server), NewHosting, Hosting(profile), ThisDevice
```

Новые экраны: `Dest.AddServer` (без `serverId` — иначе его закроет «забытый сервер», см. часть 1), `Dest.NewNode(server)`, `Dest.NewHosting`, `Dest.Hosting(profile)` (`profileId`), `Dest.ThisDevice`. Раздел-хозяин — `Servers`. Серверы и ноды — `ListDetail.list/detail(Servers)`.

## Задачи

### T1. `ServerLink` — одно подключение
Тесты (фейковый `NodeWizardService`, считающий connect/вызовы):
- `connectRemembersServerAndHostKey` — успешный вход добавляет сервер в `knownServers` (новым первым), без паролей.
- `unknownHostKeyAsksAndTrustReconnects` — `NodeWizardException(trust)` → `hostKeyPrompt`; `trust()` пишет отпечаток в `knownHostKeys` и входит; `mismatch` помечен.
- `callToAnotherServerReconnects` — вызов для сервера B при открытом A сначала входит в B (баг старого кода).
- `idleConnectionIsOpenedAgain` — после 60 с простоя — повторный вход перед вызовом.
- `readCallRetriesOnceAfterDrop` — read-вызов при обрыве: вход + повтор; write-вызов не повторяется.
- `sudoDefaultsToPasswordLogin` — при `sudo == "password"` и входе по паролю sudo-пароль = пароль входа; при ключе — требуется ввести.
- `closeForgetsSecrets` — после `close()` пароли пусты, подключения нет.

### T2. `NodeDraft`
Тесты: из `InstalledChannel` (все типы транспортов, режим); `toTransports` — ошибки «Нужна ссылка вида https://docs.yandex.ru/edit/d/…», Mail.ru, доска; порядок (Яндекс Документ, Yandex Docs, Mail.ru, Доска, Cups) — первый = основной; `direct` не входит (он всегда есть); `changes(original)` считает изменённые поля (транспорт вкл/выкл, ссылка, режим); при изменении нужен хотя бы один транспорт кроме прямого — проверено: `node-install.sh set-transports` отказывает («нужен хотя бы один документ: без него канал не нужен»), а `apply` ставит ноду и только с direct. Ruling: у ноды «только direct» (её ставит «Быстро») режим и транспорты меняются только вместе с добавлением транспорта; «Применить» недоступно, под панелью одна строка причины. Тест `directOnlyNeedsATransportToChange`.

### T3. `NodeVerifier`
Перенос `verifyNow` старой модели с тестами на фейковом `ConnectionService`: выход с адреса сервера → успех; другой адрес → ошибка «Запрос вышел с адреса …»; Android (`NotCheckable`) → успех по сессии; `Unavailable` → повтор до таймаута; `Failed` → ошибка; чужое подключение прервало → ошибка; ожидание основного транспорта с «Хватит ждать». Таймауты — параметры (тест не ждёт 150 с).

### T4. `NodeEditorModel` (создание и изменение)
Тесты: создание «Быстро» (newChannel → plan → apply → shareLink → профиль сохранён и выбран → проверка); ошибка `plan` видна до установки; `sudo` неверный → ошибка у кнопки; изменение: черновик, `changes`, «Отменить» возвращает исходное, «Применить» → `setTransports` (режим, cookies для Яндекса) → профиль на устройстве обновлён (тот же id) → проверка; ошибка применения сохраняет черновик; «Передать вход на сервер» → `setTransports` с `cookieHeader`; уход с несохранёнными правками → `pendingLeave`; удаление ноды → `remove` и экран закрывается.

### T5. Экраны Серверов
`ServersScreen` (список: серверы, хостинг, «Это устройство»; пусто — «Приступим»-строки), `AddServerScreen` (форма, чипы недавних, «Дополнительно»: sudo, ядро; диалог отпечатка; после входа — выбор «Быстро / Настроить»), `ServerScreen` (вкладки «Ноды» / «Сервер»; строка ноды → редактор; ＋ Нода; строка «Профиля на устройстве нет» не показывается — действия в меню ноды), `NodeScreen` (шапка: имя, точка, адрес:порт; [Подключить себе] [Поделиться]; ⋮ Обновить, Удалить; транспорты строками; режим; «Дополнительно»; `ChangesBar`), новая нода — та же форма с [Установить] и `ProgressLine`.
Проверка: тесты навигации экранов (открытие ноды из сервера, «назад», замена мастера экраном ноды), каталог PNG всех экранов и состояний (пусто, вход, отпечаток, ошибка входа, ноды, нода с правками, применение, ошибка, установка) в телефоне, 320 dp ×1,3, широком окне; вычитка каждого текста.

### T6. Хостинг
Новая модель по `PhpWizardModel` (FTP или «уже залита» → транспорт → установка с проверкой) и экран ноды хостинга (запуск, остановка, панель, состояние, ключ, удалить с хостинга, убрать из приложения). Тесты — по сценариям `PhpWizardModelTest`.

### T7. «Это устройство»
Профиль, который раздаёт устройство (выбор), режим L4/L3 (десктоп, если поддерживается), порт `direct`, адрес для клиентов, [Запустить ноду]/[Остановить], QR и ссылка, когда работает. Тест модели: запуск в режиме Exit, остановка, ссылка.

### T8. Подключение к `OpenFluxApp2`
`entryProvider` нового UI: экраны Серверов вместо заглушек; меню ＋ «Свой сервер» → `AddServer`, «Без сервера» → `NewHosting`.

## Review Focus
1. Два сервера открыты по очереди — вызовы идут на нужный (T1).
2. Ушёл с ноды с правками — вопрос, правки не теряются молча (T4).
3. Обрыв SSH во время долгого входа в Яндекс — повторный вход, не «скрипт не ответил» (T1).
4. Неверный sudo — понятная ошибка у кнопки, черновик цел (T4).
5. Нода без профиля на устройстве — «Подключить себе» и «Поделиться» собирают профиль из ключа сервера (T5, `Adopt`).
